# Open WebUI flagship case — docker run record

Environment: docker with pinned version images, LLM/Embedding pointed at a local echo server
(deterministic mock model, canary differential). All tested containers bind `127.0.0.1` only,
isolated from any production website/database. Images pulled via a ghcr mirror, verified by digest,
byte-identical to the official ones.

## 1. Version differential (core result)

| Check | Layer | 0.8.11 (vuln) | 0.12.5 (fixed) |
|---|---|---|---|
| S5.file.meta / file.content / kb.get | route layer (IDOR, direct object API) | PASS | PASS |
| **S7.ref_file** | derived retrieval layer, reference another's file_id | **FAIL (leaks canary)** | PASS |
| **S8.residue_A_file** | derived store residue cross-user readable after delete | **FAIL (leaks canary)** | PASS |
| other 13 checks (S1/S2/S3/S4/S7.coll/S8.*/P) | — | PASS | PASS |
| **total FAIL / 18** | | **2** | **0** |

Result files: `ecs_owui_0.8.11_suite.json`, `ecs_owui_0.12.5_suite.json`.

**Thesis evidence: route-level authorization is correct on both versions (S5 all pass); the derived
layer leaks on 0.8.11 and is fixed on 0.12.5.**

## 2. Positive control (CVE-2026-45402, D5)

`ecs_owui_0.8.11_cve.json`:
- admin attacker path: **LEAK** (process_file uses the global `get_file_by_id`, the privileged path
  leaks).
- regular-user attacker path: **NO_LEAK** (a non-admin is blocked by the downstream defense via
  `get_file_by_id_and_user_id`).
- role-dependent reproduction, consistent with the public CVE, cited as a positive control; no new
  disclosure needed.

## 3. Version bisection (localizing the derived-layer fix window)

`d1b_probe.py` (regular user reads another's file content via chat `files:[{type:file,id:<foreign>}]`):

| Version | chat_status | own_status | verdict | note |
|---|---|---|---|---|
| 0.8.11 | — | — | **LEAK** | proved by suite S7/S8 |
| 0.9.5 | 400 | 400 | **INCONCLUSIVE** | file-reference API changed: own/foreign files both crash with `NoneType...startswith`, the probe cannot get through, not adjudicable |
| 0.10.2 | 200 | — | **FIXED** | chat normal, no cross-user leak |
| 0.11.4 | 200 | — | **FIXED** | |
| 0.12.0 | 200 | — | **FIXED** | |
| 0.12.5 | — | — | **FIXED** | proved by suite 18/0 |

**Conclusion: the derived-layer leak exists in 0.8.11 and is gone from 0.10.2 onward. Fix window =
(0.8.11, 0.10.2].** Consistent with the official CVE-2026-45402 (marked fixed in 0.9.5) — 0.9.5 falls
within the window. This dynamic probe **cannot independently pin the fix precisely to 0.9.5** because
of the 0.9.5 file-reference API change (the same request body returns a server 500/400 for any file
in 0.9.5, recovering by 0.10.2); honestly stated as "consistent with the CVE's 0.9.5 fix, not
contradicting it".

> The own-file control (`own_status=400, own_retrieval_ok=false`) is key: it rules out the
> over-reading of "400 = permission denied", proving that 0.9.5's 400 is an API-compatibility issue
> rather than an owner check, so 0.9.5 is honestly marked inconclusive rather than mis-reported as
> FIXED or LEAK.
